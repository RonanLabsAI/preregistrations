Status: preregistered; execution follows public commit of this file.

## Change from the work-order draft

The work-order draft asked how fast live-web benchmarks drift using frozen-vs-live retrieval logs, but named no public, releasable corpus. This protocol answers the same decision (whether scores from a live benchmark remain comparable over time) with two public, dated live benchmarks whose per-model, per-item scores are published. No private retrieval logs are used. The PI may reject this substitution; the outcome record will say so if that happens.

## Question

For a fixed panel of models, does a model's score on a live benchmark depend materially on which release window of items it is scored on, after adjusting for the window's difficulty or task mix? If it does, scores reported on different windows are not comparable.

## Primary analysis (LiveCodeBench)

- Items: code-generation problems with contest dates; score per model and problem is the published pass@1 (0 to 100).
- Windows: calendar quarters of the contest date (UTC). A quarter is included if it has at least 50 problems.
- Strata: the published difficulty (easy, medium, hard). Difficulty-adjusted window means are post-stratified to the pooled difficulty mix of all included quarters.
- Primary statistic: mean, over models and adjacent included quarter pairs, of the absolute change in a model's difficulty-adjusted mean score (percentage points).
- Uncertainty: 95% percentile bootstrap, 10,000 resamples, problems resampled with replacement within each quarter, models held fixed and paired, RNG seed equal to the unit seed (1).
- Decision rule, tolerance 3.0 points: **comparable** if the CI upper bound is below 3.0; **not comparable** if the CI lower bound is above 3.0; otherwise **inconclusive**.
- Secondary statistics: unadjusted mean absolute drift; median Kendall tau-b between adjacent-quarter model rankings (descriptive bar 0.8); share of raw drift removed by difficulty adjustment. All with the same bootstrap.

## Secondary analysis (LiveBench)

For each category and adjacent pair of question release dates: models with turn-1 scores on every task-matched question of both releases; questions restricted to tasks present in both releases; task-post-stratified mean absolute drift with a within-release question bootstrap (10,000 resamples, seed 1) and the same 3.0-point rule. Pairs with fewer than 5 complete models or 10 task-matched questions per release are reported as not analyzed. Judgments whose question is not in the frozen release index are counted and excluded.

## Exploratory (labelled exploratory, not a test)

For LiveCodeBench models whose leaderboard release marker is not the default placeholder (2023-04-30), the difficulty-adjusted difference between problems dated after and before the marker, with a 2,000-resample bootstrap. The markers are leaderboard metadata, not verified training cutoffs; no contamination claim is made from them.

## Arms, seeds, units

One arm (`decay`), one seed (1), one unit (`cpu-decay-1`). The analysis is deterministic given the seed.

Command: `uv run --frozen python -s analyze.py --inputs <frozen-inputs-dir> --prereg PREREG.md --prereg-url <this file's public URL> --arm {arm} --seed {seed} --expect-fingerprint <frozen fingerprint>` with outputs written to the executor's receipt directory as a native K3 result package. Code is in `harness/` and is hashed into the fingerprint.

Hardware: the Idleworks CPU executor (no GPU, nice 19, CPU and memory quotas), under a preemptible fleet claim. Expected runtime under 10 minutes.

Environment fingerprint (frozen): `cpu-x86_64|py3.12.15|numpy2.3.4|pyarrow21.0.0|lcb@f186ab50|livebench@9704e5da|code@32c7b949d487`. A different observed fingerprint stops the run before any computation.

## Budget, smoke, interruption, kill

- Budget: 0 GPU-hours; CPU only; 1 hour wall-clock cap.
- Smoke: one run of the command with 200 bootstrap resamples, recorded as a smoke attempt (not a result); it must produce a structurally valid package.
- Interruption: the unit does not checkpoint; on preemption the attempt is discarded and the unit restarts from scratch (maximum lost work: one unit, under 10 minutes).
- Kill: input hash mismatch; fingerprint mismatch; fewer than three included LiveCodeBench quarters; analysis error. A killed attempt is recorded, not hidden.

## What a result can and cannot establish

It can establish whether published live-benchmark scores move with the item window by more than the tolerance, for these models and snapshots. It cannot establish causes beyond difficulty or task mix, contamination, or the behaviour of later releases not in the snapshot.

## Outcome recording

Every run outcome (comparable, not comparable, inconclusive, killed or unrun) is recorded publicly in this repository. Posts or papers only for meaningful nulls, at the PI's chosen tier.
