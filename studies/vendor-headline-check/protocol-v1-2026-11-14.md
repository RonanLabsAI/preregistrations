# Vendor headline check v1: Ollama's DGX Spark gpt-oss:120b rates

Product: `vendor-headline-check-v1` (instance of the approved work order `vendor-headline-check`).
Template: `l3-replication` (standing approval by the PI, 2026-11-14 PT).
Frozen: 2026-11-14 (PT). No timing measurement has been taken; one 16-token plumbing request confirmed the router's stream format and was not analyzed.
Status: preregistered; execution follows public commit of this file.

## Claim under test

Ollama, "NVIDIA DGX Spark performance", https://ollama.com/blog/nvidia-spark-performance (published 2025-10-23): on NVIDIA DGX Spark, `gpt-oss` 120B MXFP4 reaches **1,169 tokens/s prefill** (the table prints `1.169k`) and **41.14 tokens/s decode**. Method stated by the vendor: Ollama v0.12.6, DGX Spark firmware 580.95.05, 10 runs, temperature 0, 500 output tokens, prompt `write an in-depth summary of this story: $(head -n200 pg98.txt)`, caching disabled. The vendor's script (gist `mchiang0610/fd7ec5d4aa776de1b07bc57de3e10b15`, version `d9679b9f3aea24aebfa627a999186a3349e27f73`) reads Ollama's server-side `prompt_eval_*` and `eval_*` counters and unloads the model between runs.

Why this claim: it is the engine vendor's own headline for exactly our hardware class and model, and it is the number capacity planning would rely on when moving daily serving onto DGX Sparks.

## Question

On our DGX Spark serving the same model through our current production engine and configuration, are single-stream decode and prefill rates consistent with the vendor's numbers?

## Arm and environment

One arm (`vendor`), seed 1 (sampling seed 0 is sent with every request, as in the vendor script), unit `s3v-1`.

Serving stack (frozen): one DGX Spark (GB10), driver 580.142, Ollama 0.32.4, model `gpt-oss:120b` (local manifest `a951a23b46a1`, model blob `sha256:6be6d66a3f546d8c19b130dc41dc24b2fc159f84ffbc76a0ee0676205083cf5a`), context 65,536, `OLLAMA_NUM_PARALLEL=8`, flash attention on, model resident, reached through LiteLLM v1.104.1 route `gpt-oss`. The current public registry manifest for `gpt-oss:120b` lists a different model blob (`sha256:a5b03e4c...`) with identical template, license and parameter layers; which blob the vendor used is not stated. Weight identity with the vendor's run is therefore not verified.

Environment fingerprint (frozen): `gb10|drv580.142|ollama0.32.4|gpt-oss120b-blob@6be6d66a3f54|ctx65536|np8|fa1|litellm1.104.1|route=gpt-oss|c1|code@f55014b1e2d9`.

Known, declared differences from the vendor method: newer engine and driver; model kept resident (unloading a production resident is not permitted); prefix caching defeated by a unique 8-hex-character prefix on every prompt instead of unloading; rates timed at the client through the router instead of read from server counters; a production-serving configuration (context and parallel slots) instead of defaults.

## Procedure

Twenty sequential paired trials at concurrency 1. Each pair is a short control request (`[nonce] hi`, 16 output tokens) followed by the long request (`[nonce] ` + prompt, 500 output tokens), both streamed with temperature 0 and seed 0. A pair is valid if both requests return usage, the long one generates at least 100 tokens, and the executor's read-only service status shows no foreign in-flight request immediately before each request. Invalid pairs are retained in receipts and up to 10 extra pairs may be run to reach 20 valid pairs.

## Metrics

- Decode rate per long request: `(completion_tokens - 1) / (time of last streamed delta - time of first streamed delta)`. Client timing includes streaming transport, so it can only understate the engine's rate.
- Prefill rate per pair: `(prompt_tokens_long - prompt_tokens_short) / (TTFT_long - TTFT_short)`, which cancels fixed router, network and template overhead.
- Summary: medians over valid pairs with distribution-free order-statistic confidence intervals (coverage at least 95%; for n=20, the 6th and 15th order statistics, 95.9%).

## Decision rule

For each metric, with a band of plus or minus 10% around the vendor number (decode 37.03 to 45.25; prefill 1,052 to 1,286 tokens/s): **below claim** if the CI upper bound is below the band; **above claim** if the CI lower bound is above it; **consistent with claim** if the CI lies inside the band; otherwise **inconclusive**.

## Execution

The job runs on the serving Spark's Idleworks worker under the queue's preemptible fleet claim, only when the resident service is idle. It triggers a fixed controller-side runner (`harness/bench.py`) over an authenticated one-use channel; the runner holds the router credential locally and reaches the model only by route name. Outputs form a native K3 result package.

## Budget, smoke, interruption, kill

- Budget: 1 GPU-hour (expected under 15 minutes of model time).
- Smoke: two pairs through the same path, recorded as a smoke attempt, not a result.
- Interruption: production traffic always wins. A foreign in-flight request invalidates that pair; eviction stops the unit, discards the attempt and restarts from scratch (maximum lost work under 15 minutes).
- Kill: prompt hash mismatch, fingerprint mismatch, fewer than 20 valid pairs after 30 attempts, or any change to the resident model or engine during the run. Killed attempts are recorded.

## What a result can and cannot establish

It can establish whether the vendor's single-stream numbers hold for the same model on the same hardware class as we actually serve it. It cannot attribute a difference to engine version, driver, weights blob, configuration or measurement point, and it does not measure multi-user throughput.

## Outcome recording

Every run outcome, including inconclusive, killed and unrun dispositions, is recorded publicly in this repository. Posts or papers only for meaningful nulls, at the PI's chosen tier.
