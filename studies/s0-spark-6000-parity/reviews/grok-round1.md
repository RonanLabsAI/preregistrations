The protocol cannot support a hardware byte-identity verdict. The chip contrast is confounded, FAIL names the wrong factor, and the frozen analysis never checks that the assigned treatment actually ran.

1. **Blocker.** Question: “the same model, prompts, request body and serving flags.” Serving section: “Allowed difference: `--gpu-memory-utilization` is 0.85 on the RTX PRO 6000 … and 0.25 on the Spark. The difference changes KV cache size and so the scheduler's batches. Batch invariance should make that irrelevant.” Later: “Batch invariance is a within-device contract; identity across devices is not promised.” And the pin of `--max-num-batched-tokens` / `--max-num-seqs` is justified because “a different memory reading cannot change them,” while the memory reading is still free to change GPU block count. `gpu_memory_utilization` is a fraction of total device memory, so 0.85 on a 96 GiB card and 0.25 on a 128 GiB shared GB10 are different absolute KV pools. That changes preemption, prefix-cache hits, and CUDA-graph capture. The within-6000 pair (c128 vs c16) stays at 0.85, so it never enters the Spark’s cache regime. A cross-pair PASS/FAIL is therefore not a same-flags chip result. **Fix:** make the primary contrast matched absolute KV (`--kv-cache-memory-bytes` or 0.25 on a 6000 arm as well as the Spark), `--enforce-eager`, prefix caching off, and log `num_gpu_blocks`. Keep 0.85 only as a separate V1-deployment arm with its own estimand.

2. **Blocker.** “The attention backend is left on auto, and the backend each server selects is read from its log and reported.” It is not in `s0_job.py` receipts, not in `units[...]`, and not in the PASS/FAIL rule. sm_121 vs sm_120 can select different backends under auto. A mismatch is then “R1 treats hardware as a factor” when the factor may be the backend. **Fix:** pin one backend; write it on every receipt; if the two sides differ, verdict is `INCOMPLETE` (protocol violation), not PASS or FAIL.

3. **Blocker.** “FAIL if they are complete and either pair has any mismatch” and “R1 treats hardware as a factor for that model.” “A FAIL is a counterexample to cross-device identity under the documented batch-invariant contract.” The within-6000 pair is same hardware, different client concurrency. If only that pair mismatches, the hardware pair matched and the contract (within-device) is the thing that failed; the rule still records a hardware factor. “A completed unit is never rerun to resolve a mismatch” plus “preemptible” resume locks that label forever. The card says “Mismatches are also tabulated by attempt, so a resume effect would show.” `compare()`’s mismatch objects have id, bench, lengths, and finish reasons only — no `attempt`. Spark is a single run, so a one-off glitch cannot be separated from a stable chip effect. **Fix:** two verdicts. Hardware factor only if `m-spark-c128` vs `m-6000-c128` mismatches. Batch factor only if the within-6000 pair mismatches. Cross-tab mismatches by `attempt`. Add a same-card, same-flags, same-concurrency replicate; if that replicate mismatches, or the two sides’ attempt sets differ, verdict is `INCOMPLETE`, not a hardware FAIL.

4. **Blocker.** Units are “`--unit q17-spark-c128=/path`”. `s0_job.py` writes id, bench, output, finish_reason, token counts, latency, and attempt. It does not write model, image id, `uname -m`, driver, card id, concurrency, memory utilization, server args, or backend. `analyze.py` will PASS two copies of one 6000 run if they are labeled spark and 6000. `load_unit` uses first-line-wins and `complete` requires `dup == 0`, and the verdict returns `INCOMPLETE` before it looks at mismatches. A duplicate line turns a finished mismatch into a rerunnable `INCOMPLETE`, which contradicts “a mismatch is the result.” **Fix:** every line carries the treatment; `analyze.py` refuses mixed or off-protocol metadata; any mismatch on the kept row is FAIL even when `dup > 0`; hash the first complete file and reject a silent replacement.

5. **Blocker.** “The result has the same image ID on every host” and that ID is the proof the serving stack matched. DGX Spark (GB10) is aarch64. A discrete RTX PRO 6000 is an x86_64 PCIe card. A `docker build` of `Dockerfile.bi` on those two CPUs does not produce one native rootfs; a shared id is either a manifest-list digest (different wheels per platform) or a check of the wrong identifier. Host driver is also unpinned. Software identity is confounded with the chip. **Fix:** pin the platform-specific manifest digest per host, record `os/arch` and the driver version in the receipt, and treat an arch or driver mismatch as a different factor.

6. **Should-fix.** “The control does not change the verdicts. If it shows no mismatch, the write-up must say … a PASS is then weaker evidence.” The only control is `q17-6000-nobi-c128` vs `q17-6000-nobi-c16`. Granite has no nobi arm, despite “each family gets its own check.” Nothing logs realized vLLM batch sizes, so 1,179/1,179 on the control is compatible with deterministic kernels, with c16 and c128 collapsing to the same server batches, or with a set that cannot show noise. In code, `control_sensitive` is true whenever `all_identical` is false, including missing rows, and a missing control leaves Qwen `PASS` and pooling allowed. **Fix:** per-model nobi pair on one card; log scheduler batch sizes; machine-readable verdict `UNINFORMATIVE` (no pooling) when the control is missing, incomplete, or fully identical; set `control_sensitive` only for a complete pair with a real string mismatch.

7. **Should-fix.** “PASS if all four units are complete and both pairs are identical on 1,179/1,179.” The unit table and `PRIMARY` have three units and two pairs per model (spark-c128, 6000-c128, 6000-c16). There is no fourth unit. **Fix:** change the rule to those three, or add the missing unit to the table and to `PRIMARY` and say what contrast it is.

8. **Should-fix.** Qwen hashes omit `generation_config.json`, `tokenizer_config.json`, and any separate chat template. Granite hashes omit `config.json` as well (only shards, `tokenizer.json`, and a revision id). “Copies … were checked equal” is not a hash of those files. Servers apply the chat template, but `compare()` never gates on `n_prompt_tokens`. A template or config drift is a hardware FAIL under the current rule. **Fix:** hash those files in the card; if prompt-token counts differ for an id, verdict is `INCOMPLETE`.

9. **Should-fix.** “RTX PRO 6000 units may run on either of the lab’s two cards.” The within-6000 pair and the Qwen control can be cross-card, and the card is not in the receipt or the rule. Mechanism text also switches to “RTX PRO 6000 Max-Q” and “188” SMs without saying the lab cards are that SKU. RTX memory is gated only at start (“below 84 GiB”); Spark is gated during the run. **Fix:** one recorded card id for every 6000 pair that shares a verdict; SKU string must match `nvidia-smi`; runtime free-memory floor on the 6000 as on the Spark.

10. **Should-fix.** “about 1.1 GPU-hours on the Spark and 1.1 on the RTX PRO 6000s” and “Caps: 2.0 GPU-hours per hardware class,” with kill = study stop. Spark has 3 units; the 6000 class has 8, including c16 and two nobi runs. The 408 s scale-up covers one c128 Qwen-sized pass, not that table. A cap hit can censor the precommitted design, and the card does not say whether finished models are still judged. **Fix:** cost all 11 units, including c16 wall time; raise or split the cap; a cap hit is `INCOMPLETE` only for units that did not finish.

11. **Should-fix.** Procedure: “`analyze.py` runs once … `score.py` then runs once per unit.” Paired counts are produced only if `--scores` is passed into `analyze.py`. The one-shot `analysis.json` cannot contain the score contrasts the card requires. **Fix:** run `score.py` first and pass `--scores` into that single analyze invocation.

12. **Should-fix.** `s0_job.py`: `"output": (ch.get("message") or {}).get("content") or ""`. Missing content becomes `""`, and `analyze.py` has no minimum length, no required `finish_reason`, and no check that `n_out_tokens` is present (`None` is summed as 0). Two parser failures are byte-identical and can PASS. `first_diff` calls `.encode` on `output`; a non-string crashes `main` before `analysis.json` is written. **Fix:** store JSON null; accept only `str`; require `finish_reason` in `{stop, length}` and non-null completion tokens; if the schema is wrong, write `INCOMPLETE` and exit non-zero.

13. **Should-fix.** Overclaims. “A PASS extends our earlier result … to a third chip and a second family” — a per-model PASS does one of those, and “Their server flags were not logged, so a mismatch there cannot be attributed” applies to a match as well; agreement also decides nothing. “Counterexample to … the documented batch-invariant contract” — that sentence already defines the contract as within-device. “2606.08051 … one family (Aya) lost 2.7 to 5.1 points on another serving stack” is an F1 shift on hosted endpoints, not bitwise identity under this mode. The split-K / `sm120` family / shared-memory-branch paragraph has no file:line in the pinned tree, and it never says Granite hybrid/SSM ops are inside those kernels. **Fix:** one sentence per model; reference pairs stay out of the verdict either way; cite the kernel source in that image; state which Granite ops are covered.

14. **Minor.** `analyze.py` / `s0_job.py` never assert prompt SHA-256 `1d0ef52f…` or N = 1,179; the file you pass is the population. `main` returns 0 on FAIL. A dated amendment is allowed “before the units it affects run,” so Granite’s protocol can change after the Qwen verdict. A truncated final JSONL line makes `json.loads` throw on every resume, so the unit stays `INCOMPLETE`. **Fix:** assert the hash and 1,179; non-zero exit on FAIL; no outcome-dependent amendment under this protocol id; skip a short final line and continue.

**Overall verdict:** Do not use this card as a pooling gate until the matched-KV contrast, split verdicts, bound receipts, and per-model sensitivity control are in the frozen code.
